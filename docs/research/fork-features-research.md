# Fork feature research: tray microphone selector & post-processing reasoning level

Research date: 2026-10-25. Upstream: [cjpais/Handy](https://github.com/cjpais/Handy).
Local checkout: `main` @ `73c095857bc4eadff097f64767c40ad129cc372d` ("feat: transcribe files into history (#2315)").

## TL;DR

- **Feature A (tray mic selector): no open upstream PR and nothing pullable as-is.** Two PRs implemented it — [#1317](https://github.com/cjpais/Handy/pull/1317) and [#1837](https://github.com/cjpais/Handy/pull/1837) — both closed unmerged, and both target a tray/audio API that has since been rewritten. Demand is live in [Discussion #1803](https://github.com/cjpais/Handy/discussions/1803) (last activity 2026-10-21). Port one of the old diffs; do not expect a merge/cherry-pick.
- **Feature B (reasoning/thinking level selector): no upstream implementation, open or closed, of a _level_ selector exists.** Upstream intentionally forces reasoning **off** (`"none"`) for Custom + OpenRouter post-processing, sends **no reasoning field at all** (provider/model default) for the other built-in providers, and the maintainer explicitly rejected adding a user toggle in [#1350](https://github.com/cjpais/Handy/pull/1350). The level idea lives only in [Discussion #1378](https://github.com/cjpais/Handy/discussions/1378). A fork must build this itself; #1350's binary toggle is the nearest scaffolding.

## Feature A — Tray right-click microphone / input-device selector

### Current state in this codebase

- The tray menu has an ASR **model** submenu only; there is no microphone submenu. Idle menu items are built in `build_menu()` at `src-tauri/src/tray.rs:546-586` (model `CheckMenuItem`s with ids `model_select:{id}` at `src-tauri/src/tray.rs:556-561`, then Unload Model, Settings, Check for Updates, Quit), and clicks are handled in `on_menu_event` at `src-tauri/src/lib.rs:285-345` (model branch at `src-tauri/src/lib.rs:325-343`). There is no `mic_select:` handling anywhere in `src-tauri/src` (search: `mic_select` → 0 hits).
- The setting a selector would drive already exists: `selected_microphone: Option<String>` (`None` = system default) at `src-tauri/src/settings.rs:427`, default `None` at `src-tauri/src/settings.rs:989`.
- The reusable backend pieces already exist but are now **async**: `get_available_microphones()` at `src-tauri/src/commands/audio.rs:204` (returns a synthetic `Default` entry plus `handy_recorder::list_input_devices()` results, run via `spawn_blocking` because "cpal device enumeration can stall"), `set_selected_microphone(app, device_name)` at `src-tauri/src/commands/audio.rs:236` (persists the setting, then `update_selected_device()` on a blocking thread), and `get_selected_microphone()` at `src-tauri/src/commands/audio.rs:257`.
- The tray was rewritten to a single-writer snapshot design in commit `5ec2276a` ("single writer tray icon (#1952)", 2026-08-23; `git log -- src-tauri/src/tray.rs`). Menu contents are derived from a `MenuInputs` snapshot (`src-tauri/src/tray.rs:57-69`) computed in `compute_desired()` (`src-tauri/src/tray.rs:322-352`); if two snapshots compare equal the menu is not rebuilt (`src-tauri/src/tray.rs:54-55`). Any mic selector must add the device list + selection to `MenuInputs`, or the checkmark/list will go stale. The snapshot is computed on the calling thread on purpose (`src-tauri/src/tray.rs:248-250`).
- Tray strings are generated from the English `tray` keys in `src/i18n/locales/en/translation.json`; to add an item you add the key there and use `strings.<field>` in `tray.rs` (`src-tauri/src/tray_i18n.rs:10-13`).

## Feature B — Reasoning / thinking level selector for AI post-processing

### Current default in this codebase (there is no level setting)

- **No user-facing reasoning/thinking setting exists at all.** The post-processing settings are `post_process_enabled`, `post_process_provider_id`, `post_process_providers`, `post_process_api_keys`, `post_process_models`, `post_process_prompts`, `post_process_selected_prompt_id` only (`src-tauri/src/settings.rs:468-481`). The provider struct likewise has no reasoning field — just `id`, `label`, `base_url`, `allow_base_url_edit`, `models_endpoint`, `supports_structured_output`, `api_format` (`src-tauri/src/settings.rs:110-122`). There is no `reasoning`/`thinking` key in `src/bindings.ts` post-process commands either (provider/base-URL/api-format/api-key/model/prompt commands only).
- **Reasoning is force-disabled for exactly two provider ids:** `let disable_reasoning = matches!(provider.id.as_str(), "custom" | "openrouter");` at `src-tauri/src/actions.rs:248`, with the rationale comment "post-processing rarely benefits from it and it adds seconds of latency" (`src-tauri/src/actions.rs:245-247`). `git blame` dates this line to commit `148e5492` (#1809, 2026-07-31), which widened the original Custom-only behaviour from #1221 (commit `84d88f91`, 2026-04-07) to also cover OpenRouter.
- **What "disabled" sends is provider-shaped**, in `reasoning_disable_params()` at `src-tauri/src/llm_client.rs:60-85`: DeepSeek base URLs (`api.deepseek.com`) get `thinking: { "type": "disabled" }`; provider id `openrouter` gets the nested `reasoning: { effort: "none", exclude: true }`; everything else that reaches this code (i.e. Custom) gets top-level `reasoning_effort: "none"`. The request struct carries at most one of `reasoning_effort` / `reasoning` / `thinking` (`src-tauri/src/llm_client.rs:41-49`, flattened into the request at `src-tauri/src/llm_client.rs:119-120`).
- **All other built-in providers get no reasoning field whatsoever**, so the provider/model's own server-side default applies. When `disable_reasoning` is false, `ReasoningParams::default()` (all `None`, skipped in serialization) is used (`src-tauri/src/llm_client.rs:423-427`). The built-in provider list this applies to is OpenAI, Z.AI, Anthropic, Groq, Cerebras, AWS Bedrock (Mantle) and (on macOS arm64) Apple Intelligence, defined in `default_post_process_providers()` at `src-tauri/src/settings.rs:692-790` — only `openrouter` and `custom` from that list hit the disable path. This matches upstream user reports: in [Discussion #1378](https://github.com/cjpais/Handy/discussions/1378), a 2026-09-11 reply describes post-processing on "5.6 Luna" as slow, "I suspect it's doing the default medium level of reasoning", i.e. the model default showing through because Handy sent nothing.
- **Anthropic-format requests ignore reasoning entirely:** `send_chat_completion` routes `PostProcessApiFormat::Anthropic` to `send_anthropic_message` without passing `disable_reasoning` (`src-tauri/src/llm_client.rs:350-352`), and that function's request body is only `model`, `max_tokens`, `messages` (`src-tauri/src/llm_client.rs:537-544`), per its comment "thinking is off unless requested, so no reasoning fields are needed" (`src-tauri/src/llm_client.rs:519-523`).
- **Rejection fallback (already in `main`):** if a request carrying reasoning-disable fields returns HTTP 400/422, Handy retries once without them and remembers the `(base_url|model)` pair for the rest of the process so later dictations skip the fields (`src-tauri/src/llm_client.rs:87-110` and `src-tauri/src/llm_client.rs:451-487`). After such a fallback that endpoint effectively runs at its model default reasoning level. Output-side, any `<think>…</think>` block that still comes back is stripped before pasting (`strip_think_block`, `src-tauri/src/actions.rs:130`, applied at `src-tauri/src/actions.rs:326,381`).
- So, in one sentence: **the current "default level" is `none` (hard-coded, not configurable) on Custom and OpenRouter, and "whatever the provider/model defaults to" everywhere else; there is no minimal/low/medium/high choice anywhere in the UI, settings file, or request builder.**

### Can a fork pull it in as-is?

There is nothing to pull for a **level** selector — no branch implements `minimal|low|medium|high` (or provider equivalents) as a setting. Practical options for a fork:

- **#1350 as scaffolding (not as-is):** it already wires a persisted setting through `settings.rs` → a `shortcut/mod.rs` command → `bindings.ts` → `settingsStore.ts` → `PostProcessingSettings.tsx` plus locale keys (file list from `pulls/1350/files`), which is exactly the plumbing a level setting needs. But it is binary on/off, Custom-only, predates the #1809 retry logic now in `src-tauri/src/llm_client.rs:423-487`, and sits 232 commits behind `main`, so it needs a rebase and rework, not a cherry-pick.
- **Build the selector on the existing `ReasoningParams` seam:** `reasoning_disable_params()` (`src-tauri/src/llm_client.rs:60-85`) already centralises the three provider shapes, and its `ReasoningConfig.effort` / `reasoning_effort` fields accept arbitrary strings (`src-tauri/src/llm_client.rs:30-49`), so a setting can map onto: OpenAI-style `reasoning_effort: minimal|low|medium|high` (the value set quoted in #1350's body), OpenRouter nested `reasoning.effort` (same struct), DeepSeek `thinking` (`disabled` today at `src-tauri/src/llm_client.rs:65-67`; its accepted `reasoning_effort` values `high|low|medium|max|xhigh` are quoted in [issue #1342](https://github.com/cjpais/Handy/issues/1342)). The 400/422 retry-without-fields fallback (`src-tauri/src/llm_client.rs:451-487`) already protects endpoints that reject whatever the user picks.
- **Scope decisions the fork must make itself** (upstream has not): whether the setting is global or per-provider (settings today store model per provider id in `post_process_models`, `src-tauri/src/settings.rs:476-477`, which is the natural precedent); whether built-in providers other than Custom/OpenRouter (OpenAI, Z.AI, Groq, Cerebras, Bedrock (Mantle), Anthropic) should start receiving a field they currently never get (`src-tauri/src/actions.rs:248`); and what Anthropic-format requests should do, since that path currently sends no thinking parameter at all (`src-tauri/src/llm_client.rs:519-544`). Discussion #2167's raw "Extra Options JSON" is the alternative design if per-provider enums prove too brittle.
